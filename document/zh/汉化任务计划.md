## 一、架构结论（已完成调查，作为后续所有工作的前提）

1. **UI 文本分布**：大头在 Rust 侧生成（菜单/对话框标题 `const TITLE`、节点名由 `#[node_macro::node]` 自动 Title case、属性面板 `LayoutGroup/WidgetSection`），经 wasm 序列化传给前端 Svelte 渲染。前端 Svelte/TS 里另有数百条硬编码英文（~54 .svelte + 42 .ts）。
2. **上游零 i18n**：无 svelte-i18n/gettext。引入框架需重构 Rust→前端数据流，成本最高，**不做**。
3. **渲染端**：CEF/Chromium 渲染 web 页面。字体由 CSS 字体栈 + 系统 fontconfig 决定，与 Rust 二进制无关（这是与 MotrixSim egui `include_bytes!` 方案的本质差异，Rust 侧嵌字体无效）。
4. **CEF 加载链路**：自定义 scheme `resources://`（desktop/ui/src），资源来自内嵌或 `GRAPHITE_RESOURCES` 目录。注入脚本走前端构建产物即可，无需动 CEF 钩子。

## 二、总体技术方案

### A. 翻译引擎（注入式，不动上游源码逻辑）
- `frontend/public/zh/zh-dict.js`：翻译字典（public 目录随 Vite 构建进 dist，CEF scheme 下可访问）
- `frontend/public/zh/zh.js`：MutationObserver + 文本节点/属性替换引擎（覆盖 textContent、placeholder、title/tooltip、aria-label）
- `frontend/index.html`：body 末尾加两行 `<script src>`（非 module，先于 Svelte app 执行）
- 优点：upstream rebase 冲突面极小（3 个文件）；字典未命中显示原文，天然安全降级
- 注意：Rust 侧动态拼接文本（如 `format!` 版权行）只能按整句模板匹配或放行

### B. 字体链路（防"口口口"，来自 MotrixSim 实战经验）
> **经验教训（用户 MotrixSim 项目）**：首选字体不含 CJK 时，渲染器有概率落回"默认系统字体"并**误判系统有中文**，实际渲染出口口口（豆腐块）。防御：显式声明 CJK 字体，不依赖隐式回退。

- 源字体：`desktop/assets/fonts/HarmonyOS_Sans_SC_{Regular,Medium,Bold}.ttf`（已就位，共 ~24.6MB，git 跟踪；鸿蒙字体许可允许免费商用与随应用分发）
- 安装：用户级 `~/.local/share/fonts/`（无需 root），同名跳过 + `fc-cache`（脚本见任务 D）
- CSS 修改（`frontend/src/components/Editor.svelte`）：
  - `Editor.svelte:240` `font-family: "Source Sans Pro", Arial, sans-serif` → `"Source Sans Pro", "HarmonyOS Sans SC", Arial, sans-serif`
  - `Editor.svelte:123(TextLabel)/FieldInput:140` 等宽栈 `"Source Code Pro", monospace` → `"Source Code Pro", "HarmonyOS Sans SC", monospace`
  - 验证过的 family 名：`HarmonyOS Sans SC`（fc-list 确认，非文件名）
- 中西文混排：英文数字仍用 Source Sans Pro（品牌字体），中文落鸿蒙——两全
- 最终兜底：未装鸿蒙的机器 fontconfig 自动落系统 CJK（Noto Sans CJK 等）

### C. 分支策略
- `master`：与上游镜像，只 fast-forward
- `zh-main`：所有汉化提交。上游更新流程：`git fetch origin && git rebase origin/master`（或 merge，待定）
